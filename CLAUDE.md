# docket

A terminal app that runs PR reviews through the `review-code` skill in a `claude` or `codex` session, then archives and cleans up once the review is submitted. See README.md for the user-facing description.

## Layout

```
bin/                        setup, update, build, install, start, test, fmt; `-h` prints usage, except that start passes it to docket
cmd/docket/main.go          flags, the URL argument, and the mcp subcommand; the only file that imports tui or mcp
internal/core/pr/           Ref{Org,Repo,Number}, ParseRef                         pure
internal/core/reposconf/    Parse, Resolve                                         pure, filesystem via callback
internal/core/tier/         Decide                                                 pure
internal/core/review/       Record, Event, State, Fold, Decide                     pure
internal/core/requests/     PR, Fetched, Group                                     pure
internal/core/index/        Store: JSONL append under flock, Load, Compact, Stat/Changed for the watcher
internal/core/config/       config.toml, DOCKET_HOME paths, review_code_dir, codex_sessions_dir, claude_jobs_dir
internal/core/exec/         Runner: Real, Fake
internal/core/engine/       Engine interface and Paths; claude.go and codex.go implement it
internal/core/gh/           GitHub interface; shells to `gh api`
internal/core/git/          Git interface; shells to `git`
internal/core/clone/        the tier-2 clone sequence
internal/core/session/      Service: Prepare, LaunchSpec, AfterExit, Submit, DraftBody, Notes, Browse, Abandon, Refresh, StartBackground, Restart, TrustSpec, PollBackground, Requests, Teams, SaveTeams
internal/tui/               root model, its own messages, keymap, styles; the only package that runs a CommandSpec
internal/tui/msg/           the intents the screens send up to the root
internal/tui/screens/       dashboard, newreview, submit, notes, help, inbox, teams
internal/mcp/               the MCP server over stdio: list_reviews, start_review, submit_review
```

`internal/tui/msg` holds only the intents a screen sends up, and it imports nothing
but Bubble Tea. The messages the root produces for itself live in
`internal/tui/msgs.go`, so the screens never depend on the service packages those
name. `internal/tui/deps_test.go` asserts both directions. Screens turn keys into
intents and run no commands, which is what makes their `Update` testable with
synthetic `tea.KeyPressMsg` values.

Dependency direction is `{tui, mcp} -> session -> {engine, gh, git, index, clone, tier, config}`.

## Rules

- Nothing under `internal/core` imports Charm, `internal/tui`, `internal/mcp`, or the MCP SDK. `internal/mcp` imports neither Charm nor `internal/tui`, because it speaks the protocol on stdout. `internal/tui/deps_test.go` asserts both with `go list -deps`.
- `os/exec` is called in three places only: `internal/core/exec`'s `Real` runner, which runs the commands that need nothing but their output and starts the browser, waiting only long enough to catch an opener that fails at once; `internal/tui`, which runs the one command that needs the terminal; and `cmd/docket` for the `LookPath` check at startup. Every other core package builds an `exec.CommandSpec{Path, Args, Dir, Unset}` and hands it over. `deps_test.go` asserts this by reading direct imports, because `go list -deps` reports `os/exec` for every core package: they all reach it transitively through `internal/core/exec`.
- Core packages reach the filesystem, git, and GitHub through interfaces, so tests use fakes instead of a real repo or network.
- Installed `review-code` paths are configuration with defaults, never hardcoded constants.
- docket never uses an Anthropic or OpenAI API key. It drives the `claude` and `codex` CLIs under the user's subscription.
- Pin exact versions of the Charm modules in go.mod. The v2 import paths are `charm.land/...`, not `github.com/charmbracelet/...`.
- A dry run is stopped in `internal/tui`, not in a runner. Most of what a dry run must not do is a write to the index or the filesystem, so no `exec.Runner` ever sees it. `session.Explain` and `session.ExplainResume` build what would run without recording anything, and the root model reports that instead of acting. `cmd/docket` is the one exception: `EnsureDirs` and `CompactIfNeeded` run before the TUI exists, so they read the flag themselves. Reading the index still creates the home directory and the lock file, because `Store.lock` opens it with `O_CREATE` on the shared path too, so a dry run records nothing rather than writing nothing. `docket mcp` refuses `--dry-run`, because every tool records or starts something, and a server that reported doing so without doing it would mislead the agent.

## Verified facts about review-code

These were verified while planning and shape the design. Don't rediscover them.

- **review-code detects the repo from the working directory** (`~/.agents/skills/review-code/scripts/review-orchestrator.sh`, `handle_pr_review`). If the cwd is a git repo whose `gh repo view` owner/name matches the PR's org/repo, it takes the in-repo path: when `git branch --show-current` equals the PR's `headRefName`, agents read files directly (fast path); otherwise it fetches `pull/N/head` into `refs/review/pr-N` and agents read through `git show` (middle case). If the cwd is not that repo, it takes the cross-repo path: look up `org/repo` in `~/.agents/skills/review-code/repos.conf` (`helpers/repos-config.sh`, `resolve_local_clone`: case-insensitive key, tilde expansion, path must be a git repo), then `pr-worktree.sh provision` makes a blobless fetch and a detached worktree under `~/.agents/skills/review-code/.worktrees/<org>/<repo>/pr-<N>`, torn down at session end by `session-hooks/review-code-cleanup.sh`. No repos.conf entry means a diff-only review.
- **review-code creates no draft review on your own pull request** unless it is passed `--self` (`SKILL.md` line 52, "for testing"). The session runs to completion and then skips both the draft and the Suggested Comments, so docket finds nothing on GitHub and reports `unreviewed` however well the session went. `Prepare` compares the pull request's author against the signed-in login and sets `Record.OwnPR`, and `engine.reviewArgs` passes `--self` for it. Verified by a real background run against docket's own pull request 4, whose transcript reads "`is_own_pr` is true and `--self` was not passed, so both the draft review and the Suggested Comments section are skipped".
- **`--force` does not answer every review-code prompt.** It skips the pre-flight context clear (`SKILL.md`, Step 2). A review file that already exists is a second prompt, in `handlers/review.md` under "If `file_info.file_exists` is true", and only `--overwrite` or `--append` answers that one. docket asks that question itself before launching: `session.Existing` reports the notes file and my reviews on GitHub, the new review screen offers view and ask, append, or overwrite, and the answer is stored as `Record.Intent`. `engine.reviewArgs` passes `--append` or `--overwrite` from it, interactive and background alike, so review-code's own prompt never appears.
- **A leftover pending draft does not block a new review.** review-code's `create-draft-review.sh` deletes my existing pending review and posts a new one. With `--append` it first copies the old draft's comments on files outside the delta.
- **`/review-code find <N>` is not usable for questions.** It prints the notes path and the first lines of the notes and stops, and it resolves the target from the working directory, so it cannot run from the tier-1 scratch directory. The question-and-answer session (`Engine.Ask`) is a plain `claude` or `codex` session whose first message names the notes file and the pull request.
- **Review notes** live at `~/.agents/skills/review-code/.reviews/<org>/<repo>/pr-<N>.md` (`helpers/config-helpers.sh`, `get_review_root`). They persist independently of any worktree or clone, so docket records the path and never moves the file.
- **Submission is always explicit.** review-code's `create-draft-review.sh` posts a review with no `event`, which GitHub stores as `PENDING` with `submitted_at: null`. Submitting is `POST /repos/{o}/{r}/pulls/{n}/reviews/{id}/events` with `APPROVE`, `COMMENT`, or `REQUEST_CHANGES`. `~/.dotfiles/bin/pr-review.sh` (`fetch_pending_reviews`, `cmd_submit`) is the logic docket ports, except that docket paginates and that script does not. A submit that leaves `body` out keeps the pending review's body, which is review-code's summary (verified on PostHog/posthog#105871). The submit screen fills its body from the pending review and leaves `body` out when the user did not change it, because the text area rewrites what it holds (a tab becomes spaces, control characters go) and sending it back would rewrite the summary. `SetDraft` turns `\r\n` into `\n` first, because a body saved from the browser has them and the text area turns each `\r` into a line break of its own. Whether an explicit empty `body` clears the summary is unverified, so an emptied body is also left out and the screen says the summary stays. A submit of a pending review that was deleted answers 404. A second submit of a review already submitted answers 422 ("Could not comment pull request review.") and leaves its body and `submitted_at` as they were. A second pending review by the same user on one pull request answers 422 ("User can only have one pending review per pull request"). All three were verified on haacked/docket#24, a throwaway pull request.
- **Background sessions are claude's alone** (verified on 2.1.273). `claude --bg` refuses `--session-id` (`warning: --bg manages the session id`) and mints its own, so a background record carries no session id until docket reads one back. The short id is the first line of stdout, `backgrounded · <id>`, while `Starting background service…` goes to stderr; the short id is the first 8 characters of the session UUID. `claude agents --json --all` lists every session as `{kind, id, sessionId, cwd, startedAt, state, status, pid}`, where `id` is present only on background entries. A session runs as `state: working`/`status: busy` and finishes as `state: done`/`status: idle`. **A finished session keeps its `pid` and claude keeps holding it**: `claude --resume <sessionId>` refuses with "is running as a background session … Run `claude attach <id>`". `claude stop <id>` drops the `pid`, keeps the conversation, and frees it for `--resume`. So the presence of `pid` is what decides whether docket attaches or resumes. `claude rm` deletes the conversation and docket never runs it.
- **`claude --bg` refuses a directory nobody has trusted** (verified on 2.1.281). It exits 1 and prints ``Workspace not trusted. Run `claude` in <dir> once and accept the trust prompt, then retry.`` on stderr. No flag trusts a directory. `claude /exit` run in the directory shows the trust prompt, then runs `/exit` as its first message and exits 0 once the user accepts; declining exits 1 and trusts nothing (verified through a scripted terminal). The prompt's cursor starts on "No, exit". The trust check walks up from the working directory and stops at its git root (read from 2.1.281's code, not run), so a trusted parent does not cover a tier-2 clone, which is its own git root. `Claude.Untrusted` matches the stderr text and `Claude.TrustSpec` is the `/exit` command.
- **A background session that ends its turn reports `status: idle` and keeps its `pid`, and its `state` says nothing reliable about it** (2.1.281). `state` is claude's own reading of the transcript, and an ended turn has landed in three places. `state: blocked` with `tempo: blocked` came from review-code runs that posted the draft and asked whether to submit it (PostHog/posthog#105555 and #105556). `state: working` with `tempo: idle` and `output: null` came from runs that posted the draft and closed by saying how to amend it, and it stayed that way for three hours (PostHog/posthog#105890 and PostHog/posthog-android#805). `state: done` came from #105890's second turn, which answered a question and asked nothing back. All of them had a pending draft on GitHub. So `ParseStatus` sets `BGStatus.Idle` from the status and reads `state` only for `Done`. `state` has missed `done` for an ended turn but has not reported `done` for a turn still running, so `done` still reads as over. `settle` reads GitHub for an idle session that is not done: the session's own draft or submission moves the record on, and anything else leaves it running, because a session can also end its turn before it posts, at a permission prompt. "Own" is `ownWork`: a launch snapshots `PriorPendingID` beside `PriorReviewIDs`, because an append or overwrite re-review starts with my old pending draft still on GitHub and review-code replaces it only when it posts its own. The poll's `settleIdle` reads GitHub once for each stretch the session stays idle, keyed on the status file's `updatedAt`, and forgets the key once the session works again or its record moves on. `afterBackgroundExit` settles an idle session too, so opening a drafted row's session and leaving it unanswered keeps the draft rather than putting the row back to reviewing, and a failed read there keeps the row's state and puts the error on it, as `detect` does. `state: blocked` also appears in the middle of a run: job `e64beb59` reported it at 17:33 while it waited on its own reviewer agents, before it had posted anything. Whether `status` reads `idle` at such a point is unverified. If it does, the poll reads GitHub once for each change to the session's status file, and the record moves on only once the session's own draft is posted. `status` also reads `idle` for a few seconds after `claude --bg` returns, before the first turn starts, while the status file already says `tempo: active` and `detail: starting…` (probe session 651b6f55 on 2.1.281). The poll that follows a launch therefore reads GitHub once, and `ownWork` leaves the record at `reviewing`. The dashboard says a session is waiting for the user only when the listing reports it idle and the status file does not report it active (`progressFor`), and it shows claude's `needs`, or "your input" when there is none. That rule assumes a session stopped at a permission prompt reads `status: idle`. Two probes could not check it, because both background sessions ran their tool call without asking. If such a session reads `busy`, its row does not turn red and does not show the need.
- **claude's background service keeps a status file per session** at `~/.claude/jobs/<short id>/state.json` (2.1.281). docket reads `detail` (a one-line summary claude rewrites as the session goes), `tempo` (`active`, `idle`, or `blocked`, of which docket reads only whether it is `active`), `needs` (what a blocked session is waiting for, often null), `fan` (the session's sub-agents, where a finished one keeps its entry for a while with `doneAt` set, so docket counts only the entries without it), and `updatedAt`. `claude agents --json` carries none of these. The file is undocumented, so `Claude.Progress` returns an empty `Progress` when the file is missing or does not parse, and the poll carries on with the listing alone.
- **A stopped background session resumes; a held one does not** (verified both legs on 2.1.273). A finished session that was never stopped reports `state: done` with its `pid`, and `claude --resume <sessionId>` refuses it: "is running as a background session … Run `claude attach`". After `claude stop <id>` the entry keeps `state: done`, loses `pid` and `status`, and `--resume` then works. So `Live = pid != 0` is what picks attach over resume, and an old entry with no pid correctly resolves to a resume.
- **`claude --bg` returns straight away** even when its caller drains stdout to EOF, so the background service detaches its own stdio. `exec.Real` captures both streams into buffers, which would otherwise block on the pipe rather than on the process.
- **A session claude is no longer holding is over**, whatever its state says. `claude stop` on a session that was still working leaves it `state: stopped` with no `pid`, and `stopped` is not `done`, so keying only on `done` would poll it for ever. `ParseStatus` reads `state == "done" || pid == 0` as finished.
- **codex has no background mode** (0.150.1). `codex exec` is a foreground process, so a review would be a child of docket and die with it. The `app-server` daemon that `codex agents` browses is real but unreachable here: it needs the standalone installer at `~/.codex/packages/standalone/current/codex`, `codex agents` is an interactive TUI with no `--json`, and driving the daemon means speaking its socket protocol rather than building a `CommandSpec`. `engine.Background("codex")` returns false and the new review screen refuses the toggle. Revisit when the CLI is upgraded.
- **CLI facts** (Claude Code 2.1.268, codex-cli 0.150.1): `claude [prompt]` starts an interactive session with the prompt as the first message; `--session-id <uuid>` sets the id; `-r/--resume <id>` resumes; `-c/--continue` resumes the most recent conversation in the cwd; `--bg` starts a background session and prints its id; `-p/--print` is headless. `codex [prompt]` is interactive, `codex exec` is headless, and the skill is invoked as `$review-code`. `-C/--cd <dir>` and `--add-dir <dir>` are accepted by plain `codex`, `codex exec`, and `codex resume` alike (verified on 0.150.1), so resuming keeps the same working root and writable directories as the start. Launched from inside a Claude session, codex needs `env -u CLAUDECODE -u CLAUDE_CONFIG_DIR`.
- Interactive `codex` has no session-id flag. `CaptureSessionID` scans `<codex_sessions_dir>/YYYY/MM/DD/rollout-*.jsonl` and reads the first line, which is a `session_meta` object. It matches `payload.cwd` against the record's directory, with both sides run through `EvalSymlinks` because codex records the resolved path. It filters on `payload.timestamp`, not the file's mtime: a rollout is appended to for as long as the session runs, so its mtime is the end of the session, not the start.
- The rollout path's date directories and filename timestamp are **local** time while `payload.timestamp` is UTC, so `scanDays` builds its candidate directories in local time.
- **docket's session is the oldest match, not the newest.** review-code dispatches every reviewer through `codex exec` from inside the running session and passes no `-C`, so each reviewer inherits the session's working directory and writes its own rollout carrying the same `cwd` and a later timestamp. Taking the newest match therefore hands back a reviewer's thread, and `codex exec resume <sub-agent id>` answers `cannot resume an unloaded multi-agent v2 sub-agent through its parent` (reproduced on 0.150.1). `CaptureSessionID` takes the first rollout at or after the launch. A resume is still captured, because `launch` stamps `StartedAt` again and the cutoff moves past the earlier session with it.
- `scanDays` covers the start day and the day after it, and nothing else. codex files a rollout under the local date the session began, and `launch` stamps `StartedAt` immediately before handing over the terminal, so the second day only covers a launch that crosses midnight.
- A `session_meta` payload carries both `id` and `session_id`. On a fresh session they are equal. A resumed session writes a new rollout whose `id` is its own and whose `session_id` is the thread it continues. Which of the two `codex resume` accepts after a resume is **unverified**: the check needs a working `codex` CLI, and the installed 0.150.1 is too old for this account's models (`gpt-6-astra` wants a newer CLI, and 0.150.1 cannot fall back to a model a ChatGPT account may use). docket stores `payload.id` and re-captures after **every** exit, which is correct under either answer as long as a rollout is resumable by its own id. Filtering sub-agents on `session_id != id` looks tempting and is wrong: a resumed interactive session has that shape too, so the filter would drop the very rollout the next resume needs. Verify the id question when the CLI is upgraded.
- Also unverified, and settled by the first real codex run: taking the oldest match assumes `codex resume` writes a new rollout when it resumes. If it writes none, the capture finds nothing and `captureSessionID` keeps the id it already had, so a plain resume is safe either way. The case that would mis-capture is a resume that writes no rollout **and** dispatches a review from inside itself, where the oldest match after the new `StartedAt` would then be the first reviewer.
- `CaptureSessionID` matches on the record's directory and a start time, and every tier-1 record runs in the one shared `Paths.Scratch`. Two docket instances reviewing under codex at the same time can therefore each capture the other's session, because the oldest rollout after a record's cutoff may be the other instance's. It takes all three to happen: the codex engine, tier 1, and overlapping instances, which one process cannot produce on its own because the TUI hands the terminal to a single session. M3's background reviews are what make it reachable, and a per-record working directory is the fix.
- **GitHub removes a direct review request once the reviewer submits any review, a `COMMENTED` one included, and a re-request adds it back.** On PostHog/posthog-cloud-infra#9939 the user commented on the current head and was requested again two weeks later, and PostHog/posthog#99712 was re-requested after the user's review. So `user-review-requested:<login>` lists only pull requests whose request is newer than the user's last review, and the section that names the user needs no filter. **GitHub records a reply in a review thread as a `COMMENTED` review with an empty body**, and its `commit_id` is the head when the reply went up rather than the commit the thread is on (haacked/docket#23, review 5346557302). So `review.ReviewedCommits` does not count a `COMMENTED` review with no body. That also leaves out a real review made only of inline comments with no summary, and its row stays on the list. **A team's request survives such replies**: on PostHog/posthog#100734 team-feature-flags stayed requested after three replies by the user, all recorded on the current head. On #99712 the team-feature-flags request was gone after the user's `CHANGES_REQUESTED` review, and the timeline has no `review_request_removed` event. That suggests an approval or a request for changes by a member fulfils a team's request, but it is inferred from one pull request and not verified.
- **`gh pr view --json state` reports `OPEN`, `MERGED`, or `CLOSED`**, and a merged or closed pull request still reports its `headRefName` after its head branch is deleted, so `PR` does not refuse it (verified on haacked/docket#1, #2, #3, and #5, whose branches are gone, and on cli/cli#14502, closed without merging). docket stores the value as `Record.PRState` and reads an empty one as unknown, never as closed, so a record written before the field existed does not archive on its next detection.
- The installed skill directory is a copy produced by `~/dev/haacked/review-code/install.sh`. The source is `github.com/haacked/review-code`.
- Supacode has no "tab without a worktree" primitive, so docket runs in any terminal and does not talk to Supacode.

## Bubble Tea v2 specifics

- `View()` returns `tea.View`. Alt screen, mouse mode, and bracketed paste are fields on it. The v1 `tea.WithAltScreen` program options are gone.
- Keys arrive as `tea.KeyPressMsg`, matched on `msg.String()`.
- `tea.ExecProcess(cmd, callback)` is retained. Its restore path re-enters the alt screen, restarts the renderer, and re-checks the window size.
- Keep `AltScreen` constant and `MouseMode` at `tea.MouseModeNone` so the restore after a child process is deterministic.
- Never cache width or height across an exec. A `WindowSizeMsg` follows the restore.
- Keep Bubble Tea's default signal handler and never set `Setpgid` on the child. The child must stay the foreground process group of the TTY.
- `teatest` v2 is only a pseudo-version. Test screens by calling `Update` with synthetic `tea.KeyPressMsg` values instead.

## Testing

`bin/test` runs `bin/fmt --check`, `go vet ./...`, and `go test ./...`, and passes its own flags through to `go test`. The pure packages (`pr`, `reposconf`, `tier`, `review`, `index`) carry the bulk of the coverage. Use `t.TempDir()` and the `exec.Fake` runner rather than touching the network, the real `~/.docket`, or a real clone.

Two tests are worth knowing about. `internal/core/index/lock_test.go` races `Compact` against concurrent `Append` calls, and it fails when `Compact` drops its lock, so it is the test that actually covers the locking. `internal/core/session/smoke_test.go` runs against a real pull request and is skipped unless you name one:

```
DOCKET_SMOKE_PR=haacked/review-code#159 go test -count=1 -v -run Smoke ./internal/core/session/
```

That is how to check the one thing fakes cannot: that the clone sequence really lands on the head branch with files in the working tree.

`internal/core/session/smoke_background_test.go` is the same idea for a background review, and it runs a real one end to end: the launch, the id capture, the poll, the detection of the draft on GitHub, the attach, and the teardown. Name a small pull request of your own, because a large diff dispatches a dozen reviewer agents and runs well past half an hour.

```
DOCKET_SMOKE_BG_PR=haacked/docket#2 go test -count=1 -v -timeout 50m -run SmokeBackground ./internal/core/session/
```

## Where the milestones stand

M1 is in: the dashboard, the new review screen, the claude engine, post-session detection, archive with tier-2 cleanup, abandon, refresh, and `--dry-run`.

A background launch that claude refuses records `StateNotStarted` with claude's reason, rather than `reviewing`. It used to stay `reviewing` with no id, and the poll's `recoverLost` then read GitHub for it and moved it to `unreviewed`, where the next refresh cleared the reason. The poll never touches a `not_started` row, `refuseRefresh` refuses it, and the dashboard lists it under "Did not start". `enter` on one calls `Restart`. Like `Rereview`, it refuses a merged or closed pull request and takes a fresh snapshot of `PriorReviewIDs`, because a refresh skips the row and both would otherwise be as old as the refused launch. A dry run prints the `claude --bg` command through `ExplainRestart`. A refusal for trust wraps `session.ErrUntrusted`. The root then hands the terminal to `TrustSpec` for the record's directory, through a `launchMsg` of kind `launchTrust`, and when the prompt exits zero it starts every record that was waiting on that directory. A batch collects its refusals and does the same for each directory in turn. A second refusal after the prompt counts as a failure and does not bring the prompt back. A prompt that cannot run, such as one for a clone deleted in the meantime, reports that directory and still asks about the others. The reports that follow a prompt add to the status line rather than replace it, because the batch's list of the pull requests that failed is on that line and nowhere else. A launch that exits zero without printing an id still stays `reviewing` for `recoverLost`, because it may have started a session. Each poll also reads `Claude.Progress` for every running session, and the dashboard draws it on a second line under the row: the detail and the agent count, the need in the error style when the session is waiting for the user, and "no update for Nm" once `updatedAt` is ten minutes old. A row's title shrinks to fit the metadata into the terminal width, and every line on the dashboard is cut to that width. The requests screen fits its rows through the same `format.Row`.

M3 is in: background reviews under claude. The new review screen starts a review in the background unless `default_run = "terminal"` in `config.toml`, and `ctrl+b` switches between the two. `Model.Background` holds that choice and survives a switch to an engine with no background mode. The screen sends `Background && CanBackground()`, so a codex review runs in the terminal and a `tab` back to claude brings the background back. `app.New` reads the default through `Config.RunsInBackground`, which reads an empty `default_run` the way `expand` does, so a hand-built `config.Config` in a test starts in the background too. The dashboard shows what each session is doing, `enter` opens it, and `x` stops it before cleaning up. The poll is a 15-second tick the root re-arms only while something is running, so an idle docket runs no subprocesses. One `claude agents` listing answers for every record, and a session the agent no longer lists counts as finished, so a record never waits on a session nobody holds.

M2 is in: the submit screen (`s`), the notes viewer (`v`, with `e` for `$EDITOR`), and the codex engine with session id capture. `Submit` posts the event and then re-reads GitHub through the same `detect` the rest of the app uses, so archiving and the tier-2 cleanup have one code path rather than two. `Record.Submittable` accepts a `reviewing` background row that carries a `ReviewID` as well as a `drafted` one. Opening a drafted row's background session and leaving it working puts the row back to `reviewing` with the draft's id, so the poll watches it again and picks up a new id if the session replaces the draft, and that draft stays pending on GitHub meanwhile. A review that has not posted a draft carries no id, and `Rereview` clears it. A `reviewing` interactive row is refused even with an id, because resuming a drafted row keeps the id, its session is open in a terminal (possibly another instance's), and the archive after a submit would delete the clone under it. `Archive` stops the session through `stopFinished`, which reads the agent's listing first. It leaves a session that is still working, or one whose listing fails, running and keeps its clone, because the user may have given that session other work, and it puts the reason on the record. The listing's `status` can read idle for a moment before the per-session progress file catches up, the same gap `progressFor` reads `Active` for, so `stopFinished` also reads `Progress` and leaves the session running when it says `Active`, rather than stop a session that has just started a new turn. Because the poll only rereads GitHub once a `reviewing` row's session goes idle, the row's `ReviewID` can go stale while the session replaces or submits the draft. GitHub refuses a submit of either id and leaves the review as it was, so the re-read `Submit` makes of a `reviewing` row's reviews prevents nothing on its own: it turns GitHub's 404 or 422 into a refusal that says docket reads GitHub again once the session ends its turn. Neither stops a submit that lands while the old draft is still pending. The row then archives, and a draft the session posts afterward is one docket does not track. `msg.SubmitReview` carries the review id the submit screen showed, and the root refuses the submit when the poll has since moved the row to another id, because the user chose the event and the body for the draft they read. The submit screen leaves `APPROVE` out when the record's author is the signed-in user, because GitHub answers 422 to approving your own pull request.

M4 is in: the index watcher, the full key reference (`?`), and install docs. `Store.Changed` stats the index file every 2 seconds and compares mtime and size against the last check, so it costs no lock and no subprocess; a change reloads the dashboard the same way any other refresh does, which is what lets one instance pick up another's appends without either restarting. That reload path only ever adopts a stamp from `loadRecords`, which stats the index right before reading it; `reconcile` and `refreshAll` write to the index themselves partway through their own work, so they carry no stamp, and a local write no longer causes one redundant reload on the next tick the way it did at first. `?` is a screen like any other, `internal/tui/screens/help`, opened by `msg.OpenHelp` from dashboard and notes and closed by its own `esc`/`?`; new review and submit each hold a free-text field, so neither binds `?`. The footer (`keymap.go`'s `helpFor`) and the full help screen (`help.View`) both read from the same per-screen `help.Entry` tables, so the two key lists cannot drift the way they did before that table existed. The root draws every screen inside a margin (`marginX` and `marginY` in `styles.go`), and `inMargins` cuts any line wider than the room inside it, so a screen that does not fit its own lines to the width still keeps out of the right margin. The footer wraps between hints through `format.Wrap`, so a narrow terminal shows every key on more lines rather than cutting the footer off. `fit` runs after every message, once the spinner has started, and sizes the screens by measuring the text `chrome` draws above and below the screen, the same text `View` joins, so a footer or a status that wraps leaves the pane less room rather than pushing the footer off the bottom. The submit and new review fields narrow below their usual 60 columns to fit. While the new review screen or the requests screen asks what to do with an existing review, the footer is only `ctrl+c quit`, because the question lists its own keys. Startup already compacts the log when it carries more than five events per record.

Work in flight is drawn with one spinner that the root owns, in `styles.Busy`, which is never faint. Each screen draws busy text through a `format.Spinner`, which the root sets on every screen before each draw. `busy()` reads the markers of the screen on display (`dash.Busy`, `sub.Busy`, `newrev.Busy`, `reqs.Loading`) and `working`, which is the root's own text for a batch's check and start, or for `R`. A marker on a screen that is not showing does not count, because the new review screen keeps its marker after the dashboard takes over. `Update` starts the tick when a handler leaves something busy, and a tick that finds nothing busy ends the chain, so an idle docket schedules no ticks. `working` leads the status line until its work answers, and a status written meanwhile shows after it on the same line. Only the work's own answer clears `working`: `batchCheckedMsg` and `batchStartedMsg` for a batch, and `refreshedMsg` for `R`, which carries its failure too. `resetBusy` leaves `working` alone, because an unrelated failure would otherwise drop the line while the work still runs. A batch start and `R` share the one `working` line, so each refuses while the other runs. While a submit or a new review is in flight, its screen ignores every key but `esc`, and the new review screen ignores a paste too. The row carries a `submitting` marker, so `s` and `x` refuse the row until the submit answers. Every key that refuses a row with work in flight (`s`, `x`, `c`, and `enter` on a row that did not start) says why through `refuseBusy`. A finished submit switches to the dashboard only from its own submit screen, because `esc` lets the user leave while it runs. The test helper `drain` leaves out the spinner's tick, because `Update` adds it to any command that leaves something busy.

M5 is in: the review requests screen (`i`). `session.Requests` runs one REST search for `user-review-requested:<login>` and one per `teams` entry in `config.toml`, and returns them raw as `requests.Fetched`. Each team search adds `-author:<login>`, because CODEOWNERS asks the author's own team to review the author's pull request. GitHub refuses to ask the author directly, so the search that names the user needs no exclusion. On PostHog/team-feature-flags the exclusion took the search from 31 results to 27, and the four it dropped were the user's own. A team's list also leaves out a pull request the user has reviewed at its current head (`caughtUpCheck`). One further search for `reviewed-by:<login> -author:<login>` serves every team, because GitHub allows 30 searches a minute and a search per team would pass that with 15 teams. It runs when the first team has rows, a failure of it stands for every later team without searching again, and only the pull requests in both it and a team's rows are checked. A check reads `Reviews` for the commits of the user's submitted reviews (`review.ReviewedCommits`), and reads `PR` for `headRefOid` only when there is one. A pull request in the user's own section is never checked, and one in two teams' searches is checked once, because `requests.Group` lists a pull request only under the first section that has it. The checks run one after another, like the searches. A check that fails ends the checks of that team's rows, keeps every row no check found caught up, and puts the reason on `Team.Err`, and the requests screen draws the reason above the rows. The failed pull request still counts as checked, so a later team does not try it again. On PostHog/team-feature-flags this took the list from 27 to 26, dropping #95457 and keeping #100734, where the user had only replied in threads. Only a new head brings a row back. A team request made after the user's review does not, because it asks nothing new of the user: on #95457 the team was requested 26 seconds after the user approved that same commit. A team whose search fails carries the error in `requests.Team.Err`, and the other searches still run, because GitHub answers 422 to a team slug it cannot resolve. It reads the cached login or asks `gh` for one, and never calls `Login`, because `Login` writes the login to `config.toml` and a dry run may open the screen. The root keeps that and regroups it through `requests.Group` whenever the records reload, so a record's state shows on its row without searching GitHub again. It uses `gh api search/issues` rather than `gh search prs`, because the latter goes through GraphQL and refused with a rate-limit error while the REST search still answered. `requests.PR` lives in the pure package rather than in `gh`, because a screen may not import `gh`. A batch runs `Prepare` and `StartBackground` for each marked pull request in turn inside one command and reports once, because each single start answers with a `detectedMsg` that would overwrite the status line. A batch calls `session.Existing` for every marked pull request before it starts any (`checkBatch`), because review-code would otherwise ask whether to append or overwrite in a background session nobody can answer. When any has a review, the root holds the checked batch in `App.batch` and the requests screen asks once for all of them: append, overwrite, or skip them and start the rest. The answer arrives as `msg.AnswerBatch`. `esc` puts the list back with the marks kept and sends nothing, so `App.batch` stays until the next check replaces it. A pull request whose check fails is left out. Its failure shows on the status line under the question and again in the batch's report. When every check fails, nothing starts and the list keeps its marks. `resetBusy` leaves the requests screen's `Busy` alone, because the check always answers with a `batchCheckedMsg` that clears it, and an unrelated error that cleared it would let a second `enter` check and start the same batch. A dry run asks the same question and then explains the commands. `t` on the requests screen opens the teams screen, which lists the teams `gh api user/teams` returns alongside the configured ones, matched without regard to case because GitHub slugs are case-insensitive, and keeps a configured team GitHub does not list so the user can uncheck it. A failed read of the teams, such as one for a token without `read:org`, answers `teamsLoadedMsg` with the error rather than `errMsg`, so the configured teams stay on show. `enter` saves through `SaveTeams`, which writes the `teams` key alone through `config.SaveKey`, and the requests screen searches again. A failed save answers `teamsSavedMsg` with the error for the same reason, so `resetBusy` leaves both of the screen's markers alone. `Login` caches the login through `SaveKey` too, so docket writes only the keys it sets. `SaveKey` reads the file as written, so a save neither writes the defaults and expanded paths the service's `Config` holds nor undoes a hand edit to another key made while docket runs. The screen starts from the teams the service loaded at startup, so a hand edit to `teams` made while docket runs is lost on the next save from the screen, the same way the requests screen does not search for it until a restart. The root refuses `OpenTeams` while a search, a batch check, or a save of the teams runs, and says why: a save searches again, so a running search could answer after the save's search and show the old teams, and a batch check's answer and a finished save each switch to the requests screen. A read still running from an earlier visit answers the reopened screen instead of a second read, because `SetMemberships` merges idempotently and keeps the rows `Load` checked. A save that finishes after `esc` leaves the screen alone. It searches again only when the requests screen is showing and no search is running, because the next `i` searches afresh and GitHub's searches for one user run one at a time. `Service.cfgMu` guards config.toml and the two `Cfg` fields that change after startup, the login and the teams. Writers hold it, and every reader of those two fields goes through `Service.Config()`, which copies `Cfg` under it. `Login` checks the cache again under the lock, so two first detections that both ask `gh` write config.toml once. The lock covers one process: two docket instances that write config.toml at the same moment can still drop each other's key. Without the lock, the rename that lands last drops the other write's key, and a search can read the teams mid-save. Other reads of `Cfg` through its value-receiver methods, such as `NotesPath`, still copy the struct without the lock. They read only fields fixed at startup, but the copy includes the two that change. A dry run reports the teams it would write and writes nothing.

Merged and closed pull requests are handled. `session.decide` reads the pull request's state through `gh pr view` alongside its reviews, with the two reads running at the same time, and `record` archives a row that `Record.Finished` reports: an `unreviewed` or `reviewed` row whose pull request merged or closed. A `drafted` row stays open with a `merged` or `closed` tag, because GitHub accepts a review on a merged pull request and only the user can choose to submit it or drop it. `resolve` and `Rereview` refuse a merged or closed pull request through `openPR`, so `n`, a batch from the requests screen, and `u` cannot start a review there; `Rereview` reads the state again because the stored `PRState` is only as fresh as the last detection. `Existing` makes the same check only when it finds a review, which spares the user the append-or-overwrite choice without costing the common path a call. The refusal covers view and ask too, so `n` cannot adopt an existing review of a merged pull request. `State.Label` names `unreviewed` "no review posted" on the requests screen, and the dashboard titles that group "No review posted", because the state means the last session posted nothing new, not that the user never reviewed the pull request. Nothing reads GitHub at startup except for records left `reviewing`, so a row whose pull request merged while docket was closed archives on the next `r` or `R`. `r` and `R` skip a background review that is still running (`refuseRefresh`), because the poll owns it and an archive mid-session would stop the agent and delete the clone under it.

Starting from an existing review is in. Before `Prepare`, the root calls `session.Existing`, which refuses an open record from the index alone and otherwise reads the notes file and my reviews on GitHub. When it finds any, the new review screen switches to a choice step (`v` view and ask, `a` append, `o` overwrite) and resends `msg.StartReview` carrying the `Intent`. View and ask goes through `Prepare`, so it is provisioned like a review, and `adopt` sets the state directly: `drafted` with the pending review's id, or `reviewed` when there is none. `StateReviewed` exists because `Decide` cannot produce it: with my submitted review in `PriorReviewIDs` it reads `unreviewed`, and without it the row would archive at once. The question-and-answer session runs under `Record.AskSessionID` and `AskStartedAt`, kept apart from the review's `SessionID` so that `enter` still resumes the review and a background record's session is left alone. On tier 1 that session runs in the shared scratch repository with none of the pull request's files, because review-code removes its worktree when the review ends, so the first message also names `gh pr diff` and the contents API at `refs/pull/<N>/head` (verified to accept that ref). Its exit goes through `AfterAsk`, which captures the session id and then reads GitHub, because the user may have the agent submit the review or post a draft from that session. A submitted review archives the row and a new pending review moves it to `drafted`. When `Decide` reads `unreviewed`, nothing was posted, so the row keeps its state. `session.decide` applies the same rule to a `reviewed` row on every detection, which is what lets `r` and `R` read GitHub for an adopted row without dropping the `reviewed` state it cannot get back. On the dashboard, `c` asks about any row with notes, `u` re-reviews through `Rereview` (which stops a held background session, re-snapshots `PriorReviewIDs`, and records the row as `preparing` with no review id until the launch marks it `reviewing`, so another instance cannot submit the draft it is replacing), and `enter` on an adopted row with no review session opens the same choice as `u`. `c` and `u` refuse a row that is `preparing` or `reviewing` (`Record.InProgress`), in the service and on the dashboard alike. Two things still need a real run: that the prompt answers questions without starting a review, and that codex can read the notes file from that session.

The MCP server is in: `docket mcp`, in `internal/mcp`, over stdio through the official Go SDK (`github.com/modelcontextprotocol/go-sdk`). It offers `start_review`, `list_reviews`, and `submit_review`, and each runs the same `session.Service` calls the TUI makes. Every review it starts runs in the background under `engine.BackgroundName(default_engine)`, which is claude, because the server has no terminal to give a session. `cmd/docket` looks that engine's binary up at startup, so the package needs no `LookPath` of its own. One mutex runs one tool call at a time, because `PollBackground` reads the index and writes what it decided in separate steps. `list_reviews` calls `PollBackground` first, and so does `submit_review` for a record that still reads `reviewing`, because nothing else moves a finished background session on while no TUI is open, and `Submit` refuses a record that still reads `reviewing` although its draft is on GitHub. Neither calls `Reconcile`, which assumes it is the only instance. `start_review` calls `Existing` and starts nothing when it finds a review and the call carries no `existing` answer. The error says what it found and asks for `append` or `overwrite`, because review-code would otherwise ask in a background session nobody can answer. It offers no ask intent, since the question-and-answer session needs a terminal. An open `not_started` record for the pull request goes through `Restart`, which is also how a start refused for trust gets retried: the error names the directory and tells the user to run `claude` there once. Any other open record is refused with the next step for its state (`alreadyOpen`): `submit_review` for a drafted one, `list_reviews` for one still running, and `x` on the dashboard for any other, because no tool abandons a record. A `Prepare` that failed after writing the record gets the `x` advice too, since a row left `preparing` with an error otherwise reads as setup still under way. A launch that exited zero without a readable id says a session may have started, because `StartBackground` leaves that record `reviewing` for `recoverLost`. No tool sets `readOnlyHint`, because `list_reviews` records what it finds and can archive, which stops the session and deletes the clone. `start_review` keeps the default `destructiveHint`, because an append or an overwrite replaces the pending draft on GitHub. `submit_review` reports a poll's failure only when the record is still not submittable afterwards, and a record the poll archived gets its own message rather than a pointer to `start_review`. The input schemas limit `existing` and `event` to their values through `jsonschema.For` with an `Enum` added, because the struct tags carry only descriptions. The `existing` enum includes the empty string, because agents send one for an optional field they have no value for. `list_reviews` reports only open records. A running session's progress is waiting by `BGStatus.Waiting`, the rule the dashboard draws too, and carries claude's own detail and need rather than the dashboard's fallbacks, which exist only to draw the row. Abandon, ask, and re-review are not tools.
